# SAR-Agent 项目原理讲解（面试复习版）

> 目标读者：项目作者本人，用于面试前复习与临场应答。
> 每节先给"30 秒版本"（面试口头表述），再给"深入细节"（被追问时的第二层）。

---

## 1. 系统全景

**30 秒版本**：系统分四层——Gradio 表现层、Agent 编排层、工具层、数据层。感知（图里有什么）交给 YOLOv8，认知（是什么意思、下一步做什么）交给 GLM-5.3-Flash Agent，两者通过 Function Calling 解耦。界面按钮直调工具层保证稳定性，对话框走 Agent 循环提供灵活性，两条路径共用同一套工具函数。

**深入细节**：

- 为什么分层？**检测与解读解耦**是整个系统的核心决策：LLM 不直接看图。所有数字（目标数、坐标、置信度）只能来自检测器落盘的结构化 JSON，从架构上掐断了"模型编造检测结果"的可能。这也是回答"怎么防幻觉"的第一层答案。
- 两条调用路径：按钮路径是确定性的（演示最稳），Agent 路径是概率性的（灵活）。共用工具函数保证两边结果一致，也保证了断网时核心检测功能仍然可用。
- 数据层产物全部落盘并登记：每次检测生成 `result_id`，结果 JSON、标注图、统计图、报告都按 ID 组织，历史回看、跨会话引用都靠它。

## 2. Agent 循环（核心中的核心）

**30 秒版本**：自研 ReAct 风格循环——组装上下文（系统提示词 + 长期事实 + 最近会话）→ 模型决策 → 若返回工具调用则校验参数、执行、把 JSON 结果回填 → 迭代（上限 8 轮）→ 模型不再调工具时给出最终回答并写回记忆。用 GLM 原生 Function Calling 协议而不是 LangChain。

**深入细节**：

- **为什么不用 LangChain**：①循环、停止条件、记忆注入全部显式可查，调试不进黑盒；②只依赖 openai SDK 一个重依赖；③每一层都能向面试官讲清原理。LangChain 的价值在生态（Retriever/Memory 组件），当需求只是"一个可控的工具循环"时它是负资产。文档里也留了对照实验的扩展路线。
- **Function Calling 协议**：请求侧传 `tools=[{name, description, parameters(JSON Schema)}]`，模型返回 `tool_calls=[{id, name, arguments}]`；执行后以 `role=tool, tool_call_id=...` 回填。GLM 的 OpenAI 兼容层完全支持。工具描述是"给模型看的 API 文档"——写清什么时候该用/不该用，直接决定工具选择准确率。
- **四个防御机制**（每个都是真实教训）：
  1. **参数防御**：LLM 产出的参数不可信，先做类型校验、路径白名单、数值夹逼，非法时返回错误 JSON 让模型自纠而不是抛异常；
  2. **停止条件**：`MAX_STEPS=8` 防死循环；到达上限时不是报错，而是把已获得的工具观察交给模型做一次兜底总结；
  3. **失败不中断**：任何工具异常包装成 `{"ok": false, "error": ...}` 回填，模型可以选择重试、换参数或如实告知用户；
  4. **上下文经济**：工具结果回填截断到 4000 字符，逐框明细通过单独的 `get_detection_detail` 按需取。
- **实测迭代**（agent.md §9.1）：回归套件三轮 80%→85%→90%。失败案例：模型"记住偏好"只口头答应不调 save_memory（提示词补"必须调用并说明已保存"）；"再来一份 PDF"不重新生成（补"再来一份=重新生成"）；跨图对比凭对话记忆（补"必须经工具核实"）。**经验：提示词规则要写成"必须 + 动作 + 排除情形"，并且每改一条都要跑回归防规则间冲突。**

## 3. 记忆系统

**30 秒版本**：三层——L1 会话缓冲（最近 20 条消息拼进上下文）、L2 长期事实（用户偏好，SQLite 的 facts 表，渲染进系统提示词）、L3 检测档案（每次检测的哈希/参数/统计，支撑"刚才那张图"的指代和跨会话查询）。重启后偏好和历史都在。

**深入细节**：

- **为什么 SQLite 而不是向量库**：记忆内容是结构化事实，检索需求是精确匹配和时间排序，单文件零运维够用。向量检索是给"语义相似度"问题准备的，硬套反而引入 embedding 成本与不确定性。**按问题形态选存储**是这里的方法论。
- **指代解析**："刚才那张图/第二张"是 Agent 最容易出错的地方。两个机制：①系统提示词渲染"最近一次检测的 result_id"作为 session_hint；②`query_history` 工具让模型主动查档案。实测中这曾是最大的失败来源（见 §2 迭代记录）。
- **L3 与图像哈希**：同一张图重复上传可通过 md5 识别"这张之前分析过"，为"增量对比"提供天然锚点。

## 4. 防幻觉设计

**30 秒版本**：三道防线——①架构上 LLM 不看原图，工具 JSON 是唯一事实来源；②提示词铁律禁止编造数字、区分"事实"与"推断"；③验收上有数字一致率抽检（回答中的数值必须能在 result JSON 里找到）。

**深入细节**：为什么不让多模态模型直接看图？①视觉对"精确计数"不可靠；②不可溯源——检测数字错了能查检测器，模型"看图说出"的数字无从审计；③CPU 部署下省一条视觉链路。模型视觉能力保留为扩展点（对低置信度框做二次核对），但"事实来源"纪律不变。

## 5. YOLOv8 与小目标

**30 秒版本**：YOLOv8 是 anchor-free 单阶段检测器：骨干 CSPDarknet 提特征、PAN-FPN 融合多尺度、解耦头分别出分类与回归，回归用 DFL 分布式焦点损失，正负样本分配用 TaskAlignedAssigner。本项目数据是 640×640 的 SAR 舰船图，框面积中位数只有约 600 px²——典型小目标场景。

**深入细节**：

- 小目标为什么难：下采样后小目标在深层特征图上只剩不足 1 像素；SAR 还有斑点噪声（相干成像固有乘性噪声）让背景像目标。
- 工程对策：①推理 imgsz 与训练一致（640），不缩小输入；②置信度阈值默认 0.25 偏宽松，让界面可调，用"NMS IoU + 阈值滑条"让使用者自己平衡虚警/漏检；③演示图选目标较大的场景；④训练阶段可用更大 imgsz、mosaic 增强、P2 高分辨率检测层（扩展项）。
- 指标含义（面试常问）：mAP@0.5 = IoU 阈值 0.5 下各类别 AP 的平均；mAP@0.5:0.95 = IoU 从 0.5 到 0.95 步长 0.05 的平均，更严格；Precision/Recall 是虚警/漏检的两个方向。评估时两个权重必须在**同一个** test 集上跑才可比（`eval_compare.py` 保证）。

## 6. 数据与训练

**30 秒版本**：HRSID_OPENSSDD v2（HRSID 与 SSDD/OpenSARShip 合并版，Roboflow 导出）：6735 张 640×640、19435 框、单类 ship，train/valid/test = 4717/1346/672。COCO 格式，自写脚本转 YOLO txt（归一化中心点宽高），Ultralytics 训练。

**深入细节**：转换脚本的关键点——bbox 是 [x,y,w,h] 绝对像素，YOLO 要 [cx,cy,w,h] 归一化；无目标图像不写标签文件（作为背景图参与训练）；图像直接复制组织成 images/labels 平行目录。4GB 显存约束下的选择：yolov8n、batch 6~8、AMP 混合精度。

## 7. 工程踩坑实录（讲"解决问题能力"的素材）

1. **torch WinError 1114**：torch 2.8/2.9 在本机 import 即崩（c10.dll 初始化失败）。排查路径：排除 VC++ 运行库缺失 → 逐个 ctypes 加载依赖 DLL → 解析 PE 导入表确认静态依赖齐全 → 判定为加载期初始化失败 → 换 2.5.1 正常 → 锁定版本并在 CI 里固定。**方法论：从"最小复现 + 二分变量"入手，别急着重装系统。**
2. **系统代理劫持 localhost**：Gradio 启动自检 127.0.0.1 收到 502（代理返回的）。修复：进程内合并 NO_PROXY。**教训：HTTP 客户端库默认继承环境代理，本机回环也要显式豁免。**
3. **中文路径 × OpenCV**：cv2.imread 在 Windows 上读不了非 ASCII 路径。修复：`np.fromfile + cv2.imdecode` / `imencode + tofile` 封装成统一读写函数。
4. **Gradio 6 API 变迁**：Chatbot 移除 type 参数（messages 成为唯一格式）、gr.update 由组件实例返回取代。**教训：锁版本之外，UI 冒烟测试（build_demo() 能构建）要进 CI。**
5. **上传文件白名单**：Gradio 把上传存到自己的临时目录，被自家安全白名单拦截。修复：界面层先归档进受控目录再送检——顺带让 Agent 能发现上传图、历史回看不失效。**教训：安全边界要画在数据入口，而不是工具内部打补丁。**

## 8. 高频追问速答

| 追问 | 速答要点 |
|---|---|
| 为什么不用 LangChain/AutoGen？ | 需求是一个可控工具循环，不是生态；自研 200 行全透明，每层可讲清；LangChain 留作 RAG 扩展的对照 |
| Agent 怎么防死循环？ | MAX_STEPS + 兜底总结 + 工具超时 + 同参数去重 |
| 怎么防幻觉？ | 检测/认知解耦，JSON 唯一事实来源 + 提示词铁律 + 数字一致率抽检 |
| 记忆怎么做？为什么不用向量库？ | 结构化事实用 SQLite 三层；语义检索才需要向量，按问题形态选存储 |
| 检测权重哪来的？ | 开源社区 SAR 权重起步，后自训练替换；无 GPU 时 CPU 短时试训兜底 |
| 小目标漏检怎么办？ | 输入尺寸不缩、阈值可调、演示图筛选；训练侧大 imgsz/mosaic/P2 层 |
| 20 条回归怎么判分的？ | 工具选择 + 关键内容 + 数字与 JSON 比对，脚本自动判分；区分基础设施失败与行为失败 |
| 下一版做什么？ | 视觉二次核对、向量 RAG、批量评测面板、ONNX 导出提速 |
| 系统的局限？ | 单机单用户；LLM 合规是概率行为靠回归兜底；小目标漏检依赖训练改进 |
| 最难的一个 bug？ | torch DLL 1114：两个干净 venv 复现 → PE 导入表逐一排除 → 定位加载期初始化失败 → 版本二分到 2.5.1 |
